# 简记 · 离线优先的统一账本

一个「断网也能记、联网自动同步、记下就改不了」的记账系统。主应用只有一套账本、一套界面和一条记录流程：无论是否联网，都先在浏览器完成加密、签名和本机封存；恢复网络后，待同步记录按顺序自动上传。

## 核心能力

- **离线优先**：首次成功打开或安装应用后，应用外壳可离线加载。新身份可以离线创建，记录写入 IndexedDB 待同步队列；断网刷新后仍可用助记词解开本机记录。
- **联网自动同步**：监听网络恢复、页面重新可见和定时连接检查，按每批最多 50 条上传。也可点击顶部同步状态立即执行。
- **幂等与重试安全**：服务端按记录哈希识别已有记录。即使“写入成功但响应丢失”，重试也只会确认原记录，不会重复入账。
- **分叉保护**：本机已确认记录必须仍是服务端历史的严格前缀；另一设备形成不同历史时暂停同步，绝不自动覆盖或合并。
- **客户端加密**：摘要在浏览器中用助记词派生的密钥加密后才进入本机数据库或服务端。明文只存在于当前页面内存，服务端只见密文、不可逆账本标签、哈希和签名。
- **只追加与红字冲销**：没有修改或删除路径。记错时追加一笔等额反向记录，原记录与冲销记录都永久留痕。
- **公开验证与外部锚定**：公开层只放哈希承诺、签名和 Merkle 根；可用 GitHub 独立提交历史发现服务端回滚或整体替换。
- **选择性共享**：可把指定账本的数据密钥用另一身份的公钥封装后授权，撤销只影响之后的读取。
- **统一专业 UI**：总览、记账、明细、验证、共享、身份备份六个区域；支持深色/浅色主题、桌面侧栏和手机底部导航。
- **本机加密归档**：首次使用即在后台静默保存当前身份有权看到的全部账目，用独立密钥二次加密；不打断记账，可在「身份备份」查看状态、清除或恢复。
- **快速解锁与随手记**：本机 PIN 一键解锁（不必每次抄 16 个助记词）、首页一行输入完成记账、支持导出身份凭据文件离线恢复。

## 快速开始

```bash
npm start                 # 等价于 node web/server.mjs
# 默认 http://127.0.0.1:3000
PORT=8080 npm start       # 自定义端口
```

服务只依赖 Node.js 内置模块。监听地址由 `HOST` 控制，默认 `127.0.0.1`（仅本机访问）；要从局域网其他设备或容器外部访问，设 `HOST=0.0.0.0`。事件日志默认写入 `web/data/events.jsonl`，可用 `LEDGER_DATA_DIR` 指向任意目录；启动时重放并校验锚链完整性，运行时使用持久文件描述符同步追加。**生产部署必须为该目录配置持久卷**（仓库 `Dockerfile` 已声明 `VOLUME /app/data`）。

生产相关环境变量：

| 变量 | 作用 |
|---|---|
| `LEDGER_INVITE_CODE` | 设置后，注册新身份必须提供邀请码；已有身份登录不受影响 |
| `LEDGER_DATA_DIR` | 事件日志目录（容器默认 `/app/data`） |
| `LEDGER_BACKUP_PASSPHRASE` | 加密备份口令，`npm run backup` 必需 |
| `LEDGER_BACKUP_DIRS` | 多个加密备份目标，逗号分隔（兼容单数 `LEDGER_BACKUP_DIR`，默认 `./backups`） |
| `LEDGER_BACKUP_KEEP` | 每个目标保留份数（默认 30） |
| `LEDGER_BACKUP_INTERVAL_HOURS` / `LEDGER_BACKUP_DRILL_DAYS` | 守护进程备份间隔（默认 6 小时）与自动恢复演练间隔（默认 30 天） |
| `LEDGER_TRUST_PROXY` | 前置 HTTPS 反代时设为 `1`，输出 HSTS 头 |
| `LEDGER_ALLOW_TAIL_LOSS` | 仅当日志尾部是写入中断的半行时，设为 `1` 允许截断后启动 |

首次使用：

1. 生成并离线抄写 16 个助记词。助记词需配合密钥包才能恢复身份：密钥包会自动保存在本机，联网登记后也在服务端存一份加密副本。服务端不保存明文，无法代为找回。
2. 直接进入统一账本。网络不可用时也可以创建身份、记账和冲销。
3. 顶部状态显示“离线可用 / 待同步 / 正在同步 / 已同步 / 同步已暂停”。
4. 恢复网络后自动上传，不需要手动补录或导入。
5. 在「身份备份」定期导出加密账本，文件同时包含已同步与待同步记录、加密账本目录和密钥包。
6. `/verify.html?fp=<身份指纹>` 是无需登录的公开验证页，可交给对账方独立核验。

### 离线使用边界

- 浏览器第一次从未访问过应用时，无法凭空离线下载应用；至少需要成功打开过一次，或安装为 PWA。
- 本机 IndexedDB 只保存密文与签名，不保存解密后的摘要。刷新或重新打开后，需要助记词才能查看内容。
- **离线创建且从未联网登记的身份，密钥包只存在于创建它的那台设备**。此时清除浏览器数据会永久失去身份，助记词 alone 无法恢复。请联网登记一次，或提前导出加密账本备份。
- 加密的账本目录（账本名称）随身份保存在服务端，仅助记词可解开；换设备恢复后会自动合并。若本机存在无法解密的密文，界面会显式提示笔数，合计金额不会静默少算。
- 清除浏览器数据会删除尚未上传的记录。重要账目应同时保留加密导出文件。
- 同一身份在多台设备同时离线追加可能产生分叉。当前版本会检测并暂停，提供备份保护，但不提供自动合并。

## 本机加密归档（自动保存）

第一次在这台设备上使用并联网成功后，应用会在**后台静默**把当前身份有权看到的全部账目保存到本机：自己的全部记录，以及别人通过「共享授权」给你的账本记录。它不弹窗、不需要手动点保存、不改变顶栏同步状态，也只在链高或锚链头变化时增量更新。

归档层加密的是**本来就已经是密文的 `cipher`**，即双层加密；明文只在当前页面内存中，归档层从不接触。

| 项 | 参数 |
|---|---|
| 密钥派生 | PBKDF2-HMAC-SHA256 **600,000 次**迭代 + 每身份独立的 16 字节随机 salt（OWASP 量级） |
| 分域隔离 | 归档密钥与身份主密钥、账本密钥由不同 info 派生，泄露一层不牵连其它 |
| 内容加密 | AES-256-GCM，每条记录独立 12 字节随机 IV |
| 完整性 | AAD 绑定 `版本｜身份指纹｜序号｜记录哈希`，密文被搬移、替换或改索引即解密失败 |
| 防降级 | 归档参数带 HMAC 版本镜像；调低迭代次数或改版本号会被拒绝读取 |
| 长度 | 明文按 512 字节分块填充，只暴露 512B 粒度 |

**只有输入各自的助记词才能解开各自的归档**：密钥由该身份的助记词派生，换身份或换设备都解不开；归档文件从不上传，服务端与其他用户都拿不到。

归档密钥的 salt / 迭代次数 / 版本 MAC 属于**非秘密参数**，会冗余写进每一条归档行。因此「身份备份」页的「导出加密归档」生成的是一份**自包含**的迁移包：设备完全丢失后，只要保留这份文件和助记词，在任意新设备「导入加密归档」即可逐条校验并解开，不依赖原设备的 IndexedDB。「清除本机归档」与「从归档恢复」也在同一页。

### 关于「不让使用者察觉」的边界（请务必读）

我们把它实现为 local-first 意义上的**静默**——不打扰、不弹窗、无加载态、状态只在失败时变红（这也是 Evolu / Anytype 一类项目的做法）；**但没有实现为「对用户隐瞒」**：

- 欢迎页明确写出「首次使用会在本机后台自动保存一份加密归档」；
- 「身份备份」页始终显示归档笔数、占用体积、上次更新时间与失败原因；
- 提供「清除本机归档」和「从归档恢复」两个显式操作。

理由：① 处理个人信息需遵循告知同意与公开透明，静默收集并隐瞒不合规；② 即便全程加密，记录数量、时间、大小、频率等元数据仍留在设备上，业界官方文档也明确承认这一泄露面；③ 本项目立身之本是「公开可验证」，隐瞒式行为一旦被发现，信任成本远超便利。

另外，**归档只保存「你有权看到的内容」，不会把系统里其他用户的密文悄悄铺到每台设备**。全库容灾请用下面的服务端加密异地备份，那才是干净的做法。

## 本机部署（macOS 常驻运行）

不依赖云服务器，直接在一台 Mac 上常驻运行，浏览器打开 `http://127.0.0.1:3000/` 即可记账。

```bash
# 1. 取一份代码到固定目录（不要放在会被清理的位置）
mkdir -p ~/Applications && cp -R . ~/Applications/jianji-ledger

# 2. 注册为登录自启服务（launchd）
cat > ~/Library/LaunchAgents/com.wukong.jianji-ledger.plist <<'PLIST'
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
  <key>Label</key><string>com.wukong.jianji-ledger</string>
  <key>ProgramArguments</key>
  <array>
    <string>/usr/local/bin/node</string>
    <string>/Users/你的用户名/Applications/jianji-ledger/web/server.mjs</string>
  </array>
  <key>WorkingDirectory</key><string>/Users/你的用户名/Applications/jianji-ledger</string>
  <key>EnvironmentVariables</key>
  <dict><key>PORT</key><string>3000</string><key>HOST</key><string>127.0.0.1</string></dict>
  <key>RunAtLoad</key><true/>
  <key>KeepAlive</key><true/>
</dict>
</plist>
PLIST

launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.wukong.jianji-ledger.plist
launchctl print gui/$(id -u)/com.wukong.jianji-ledger | grep -E 'state|pid'
curl -s http://127.0.0.1:3000/api/health
```

要点：

- 账本数据只有 `web/data/events.jsonl` 一个文件（或 `LEDGER_DATA_DIR` 指定目录下的同名文件），**删了就没了**；建议每天复制一份到别处：`cp ~/Applications/jianji-ledger/web/data/events.jsonl ~/Documents/events-$(date +%F).jsonl`
- 登录后自动启动，进程异常退出由 launchd 拉起；`launchctl kickstart -k gui/$(id -u)/com.wukong.jianji-ledger` 手动重启
- 升级：覆盖代码但保留 `web/data/`，再重启服务
- **日志损坏时服务会拒绝启动**，而不是跳过损坏行继续以不完整历史运行。启动日志会指出损坏行号；先备份原文件再处理。仅当最后一行是写入中断留下的半行时，可设 `LEDGER_ALLOW_TAIL_LOSS=1` 允许截断该行后启动（会打印警告）。**不要删除中间行**，锚链校验仍会拒绝启动。
- 助记词需配合密钥包与加密账本备份；服务端和本机都无法代为找回明文

详见仓库根目录 `部署说明.md`。

## 容器部署

```bash
docker build -t jianji-ledger .
docker run -d --name jianji -p 3000:3000 -v jianji-data:/app/data jianji-ledger
curl -s http://127.0.0.1:3000/api/health
```

镜像内已设置 `HOST=0.0.0.0`、`LEDGER_DATA_DIR=/app/data` 并声明 `VOLUME /app/data`。**不要在没挂载持久卷的情况下运行**：容器重建会丢失整个账本。公网部署需前置 HTTPS 反向代理与访问控制。

## 备份、监控与公网部署

```bash
# 生成加密备份（scrypt + AES-256-GCM；备份前先校验整条锚链，损坏则拒绝备份）
LEDGER_BACKUP_PASSPHRASE='高强度口令' \
LEDGER_BACKUP_DIRS='/mnt/disk2/jianji,/mnt/nas/jianji' npm run backup
# 校验，并可还原出原始 events.jsonl 用于恢复
LEDGER_BACKUP_PASSPHRASE='高强度口令' npm run backup:verify -- /mnt/disk2/jianji/jianji-xxx.jsonl.enc --out /safe/events.jsonl
# 常驻守护：启动即备份一次 + 每 6 小时备份 + 每 30 天自动校验一次最新备份
LEDGER_BACKUP_PASSPHRASE='高强度口令' LEDGER_BACKUP_DIRS='/mnt/disk2/jianji,/mnt/nas/jianji' npm run backup:daemon
# 一键演练「服务关闭 + 数据目录全删」后能否完整找回（只用临时目录）
npm run drill:restore
```

`backup:daemon` 每次执行输出一行 JSON 日志（`kind:"backup"` / `kind:"drill"`，带 `ok`），可直接接监控。它用固定心跳 + 时间戳判断，**避免 30 天毫秒数溢出 `setInterval` 被截断成 1ms 疯狂重复演练**。多个目标请放在不同物理磁盘 / 主机；备份口令与助记词分开离线保管。

`GET /api/health` 返回 `degraded`、`warnings`、`logBytes`、`inviteRequired`；`GET /api/replicas` 返回加密备份份数、目标数与最后备份时间（不含路径与任何账目内容）。两者都可接外部监控；客户端总览页的「数据副本」卡片显示同样信息，并在有待同步记录时明确提示「此刻仅本机一份」。

公网部署检查清单：

1. **HTTPS 反向代理**：服务本身是明文 HTTP；公网必须前置 TLS。反代设置 `X-Forwarded-Proto: https`，或设 `LEDGER_TRUST_PROXY=1` 启用 HSTS。服务端已输出严格 CSP（`script-src 'self'`，内联脚本已外置）、`X-Content-Type-Options`、`X-Frame-Options`、`Referrer-Policy` 与 `Permissions-Policy`。
2. **注册闸门**：设 `LEDGER_INVITE_CODE`，否则任何人都能注册身份并写日志；内网给固定成员用时，建议管理员预建身份并放在 VPN 后。
3. **访问控制**：当前只有按 IP 的登录限流，没有租户隔离、配额或管理后台；公网开放前请在反代层加认证或 IP 白名单。
4. **单点约束**：`owners / grants / anchors` 全在内存，状态靠重放单个 `events.jsonl` 恢复，**只能跑一个进程**；`SECRET` 每次重启随机，重启后会话需重新签名登录。不要横向扩容多实例。
5. **加密异地备份与恢复演练**：见上文命令。

**仍未解决（需业务决策，不宜静默升级）**：标准 BIP39 助记词（含校验和）与身份级 KDF 拉伸会改变 `verifier` 派生结果，现有身份将无法登录，必须配套迁移方案；归档层已按 60 万次 PBKDF2 实施，身份体系暂保持兼容。此外仍缺多实例、租户级配额与自动对账；本项目明确声明不是审计级会计系统。

## 启用 GitHub 外部锚定

1. 把主应用部署到 GitHub Actions 可匿名访问的 HTTPS 地址。
2. 在仓库 **Settings → Secrets and variables → Actions → Variables** 新建 `LEDGER_URL`，值为服务地址，不带 `/api/...` 后缀。
3. 手动运行「发布简记外部锚点」，或等待每 15 分钟一次的定时任务。
4. 工作流生成并提交 `anchoring/latest.json`；锚点未变化时不会重复提交。
5. 打开 `/verify.html`，点击「一键核验 GitHub 锚点」，也可导入锚点 JSON 文件核对。

验证口径：

- **外部锚定有效**：GitHub 最新锚点与当前锚链头一致。
- **等待新锚点**：旧锚点仍在当前历史中，但之后还有事件未被定时任务收录；这是快照滞后，不是篡改告警。
- **核验失败**：字段不一致、跨账本引用、锚点不在当前历史中，或当前锚链自身无效。

锚点文件只含公开哈希、序号、时间和公开地址，不含密文、助记词、密钥包或账目明文。

## 开发与测试

```bash
npm run build   # 重新构建兼容旧版单文件工具
npm test        # 51 项测试：纯函数核心 + 归档/解锁密码学 + 真实进程的服务端 HTTP 集成测试
npm start       # 启动统一应用
npm run backup:daemon   # 常驻：多目标加密备份 + 定期自动恢复演练
npm run drill:restore   # 灾难恢复演练：删库 → 从加密备份还原 → 校验链与身份可恢复
```

`tests/server.test.mjs` 会启动独立进程、使用临时数据目录，覆盖身份登记、只追加写入、幂等重试、分叉拒绝、增量同步、`/api/verify` 的抗伪造、加密账本目录、重启重放、损坏日志拒绝启动、邀请码闸门、严格 CSP 与加密备份的篡改检测；`tests/archive-core.test.mjs` 单独覆盖归档的 KDF 参数、防降级、AAD 绑定与长度填充。两者都随 `npm test` 在 CI 中执行。

可选真实浏览器回归（需要本机安装 Playwright 与 Chromium）：

```bash
npm run test:browser
# 或指定现有环境：
PLAYWRIGHT_PATH=/path/to/playwright CHROMIUM_PATH=/usr/bin/chromium node tests/browser-offline.mjs
```

该回归覆盖：断网记账、断网刷新后助记词恢复、联网自动上传、重复同步去重、红字冲销、375px 手机端横向溢出和控制台错误。测试前应使用空白测试账本，不得对真实数据运行。

另有**零依赖**的 CDP 回归：只需系统装有 Chrome/Chromium，不需要 Playwright 或 npm 依赖。它会自己起临时服务与临时浏览器配置，不接触真实账本。

```bash
npm run test:browser:cdp
CHROME_PATH=/usr/bin/google-chrome npm run test:browser:cdp          # 指定浏览器
```

## 统一应用 API

公开接口（无需登录，永不含密文）：

| 接口 | 说明 |
|---|---|
| `GET /api/health` | 状态、身份数、记录数、Merkle 根、锚链头，以及 `degraded / warnings / logBytes / inviteRequired`（供监控轮询） |
| `GET /api/status` | **轻量探测**：各身份链高/链头、锚链头、授权版本，约数百字节 |
| `GET /api/replicas` | 加密备份份数、目标数、最后备份时间与日志体积；不含路径、密文或账目内容 |
| `GET /api/anchors` | 全局哈希承诺、各身份链头、近期锚点 |
| `GET /api/anchors/:fp` | 指定身份的纯哈希链与公钥 |
| `GET /api/anchor-proof` | 自包含锚定证明 |
| `GET /api/pub/:fp` | 身份公钥 |
| `POST /api/verify` | 服务端辅助校验：绑定**已登记身份**，用其 fp 与公钥逐条重算哈希并验签，链头与长度必须与服务端一致；直接传 `GET /api/entries` 的返回即可，未登记身份返回 404 |
| `POST /api/lookup` | 按助记词校验值找回加密私钥包与加密账本目录 |

会话与写入：`POST /api/challenge` → `POST /api/session`，之后使用 `GET /api/me`、`POST /api/profile`、`GET /api/entries`、`POST /api/entries`、`POST /api/entries/sync`、授权和撤销接口。

`POST /api/entries/sync` 每批接收 1–50 条记录，逐条校验并顺序追加。响应包含每条 `accepted / existing` 结果；中途遇到错误时，也会返回已处理结果，便于客户端先落盘再暂停。

**轻量探测与增量同步**：客户端每 30 秒只请求 `/api/status`。链高、链头、锚链头与授权版本都没变化时，直接跳过账目与锚定证明的拉取，也不重写本机数据库；有变化时才用 `GET /api/entries?since=<本机已有条数>` 取连续后缀，并把完整链交给严格前缀与分叉检查。**所有同步不变量仍然作用于拼合后的完整链**，增量只是传输优化。实测空闲时两轮同步只有 2 次 `status` 与 2 次 `me` 请求，零全量密文、零全量锚定证明。

`POST /api/profile` 提交用主密钥加密的账本目录，只追加、不覆盖历史；换设备恢复时由 `/api/lookup` 或 `/api/me` 取回。服务端事件为 `identity / entry / profile / grant / revoke / anchor` 六类，没有修改或删除事件。

**分叉处理**：多设备同序号写入不同哈希时，同步会暂停而不是自动合并。此时可在同步提示里「导出分叉证据」（只含密文与公开哈希，可安全交给管理员），或「以服务端为准重建本机」——该操作会**先强制下载本机完整备份**、二次确认后清除本机记录、再从服务端重新拉取权威历史；加密归档不会被删除。本机独有的待同步记录不会静默合并，需人工核对后重新录入或红字冲销。

## 安全模型

**能防**：记录被改、被删、被乱序插入；服务端单方面修改历史；同步响应丢失导致重复记录；服务端拖库直接泄露明文；摘要长度被精确推断（按 512 字节分块填充，只暴露 512 字节粒度）；事件日志损坏或中间行被删时静默启动（重放会校验锚链并拒绝启动）；用伪造链骗取服务端辅助校验结论；本机归档密文被搬移、替换、改索引或把 KDF 参数降级（AAD 绑定 + 版本 MAC）；配置邀请码后的未授权注册；借助严格 CSP 阻挡外部脚本注入与常见数据外连。启用外部锚定后，还可通过独立提交历史发现整体替换或回滚。

**不能防**：

- 客户端设备被攻破、助记词被钓鱼或泄露；本机归档密钥同样由助记词派生，因此设备失守时归档也不再安全。
- 本机归档的元数据（记录数量、时间、大小、频率）仍留在使用者设备上；归档是静默的，但不对用户隐瞒其存在。
- 服务端运营方同时替换存储、客户端证明和外部锚定仓库；外部仓库应独立控制。
- 时间、笔数、频率、IP、记录大小等元数据泄露。
- 撤销对方已经看过或保存的内容。
- 非持久托管环境导致服务端事件日志丢失；生产必须配置持久卷。
- 哈希承诺不能证明业务真实发生，也不能替代票据、合同或审计程序。

**这不是审计级会计系统**，请勿直接用于法定账簿、税务申报或需要法律效力的合规场景。

## 部署形态、使用流程与数据存续

### 怎么部署

三种形态跑的都是同一个 `node web/server.mjs`，区别只在运行位置与访问方式：

| 形态 | 做法 | 访问地址 | 适合 |
|---|---|---|---|
| 本机常驻 | 根目录 `部署说明.md` 的 launchd plist，或直接 `npm start` | `http://127.0.0.1:3000` | 一个人一台电脑，数据完全不出本机 |
| 容器 | `docker build` + `-v jianji-data:/app/data` | 容器端口映射 | 家里 NAS / 小服务器，便于迁移和备份 |
| 公网服务 | 前置 HTTPS 反代 + `LEDGER_INVITE_CODE` + 邀请码分发 | `https://你的域名` | 固定几人的团队；**不能裸奔公网** |

共同点：**单进程、单个 `events.jsonl` 是唯一权威副本**，不支持多实例；数据目录必须落在持久卷，并配置加密异地备份。

### 用户怎么用

1. 浏览器打开地址（HTTPS 或 `localhost`），点「生成我的专属密钥」，抄下 16 个助记词；可在浏览器菜单里「安装应用」变成 PWA，之后首次打开即可离线使用。
2. 首次用助记词或「身份凭据文件」恢复身份；在「身份备份」启用本机 PIN 后，之后打开只需输 PIN。总览页「随手记」一行即可记账（金额 + 方向 + 可选摘要）。记录先在本机完成加密、签名、接续哈希链，再进入待同步队列。
3. 联网后自动按序上传，服务端按哈希幂等确认；顶部状态显示「离线可用 / 待同步 / 正在同步 / 已同步 / 同步已暂停」。
4. 要给别人看某本账：在「共享授权」按对方身份指纹授权；对方在自己的设备上解密查看，撤销只影响之后的读取。
5. 换设备或服务端重建：输入助记词 → `/api/lookup` 取回加密私钥包与账本目录 → 自动解密。也可在「身份备份」导出 / 导入加密账本与加密归档。

### 一笔账能不能「永远存在」

**不能按字面保证。** 现在能保证的是「同步成功后有多份可验证的加密副本」，不是「落笔瞬间就不可丢失」。精确边界：

| 场景 | 能否找回 | 依赖 |
|---|---|---|
| 记完立刻断网，此时设备物理损坏 | ❌ **会丢** | 这一笔只在一台设备的 IndexedDB 里，还没有第二副本 |
| 记完已联网同步，之后单台设备坏 | ✅ | 服务端日志 + 其它设备的归档 + 助记词 |
| 服务器关闭但磁盘还在 | ✅ | 重启即可重放日志 |
| 服务器关闭且整个数据目录丢失 | ✅（有条件） | 必须事先跑过 `npm run backup` 并保管好备份口令 |
| 所有副本都丢，只剩助记词 | ❌ | 助记词只解开密钥，不能凭空变出密文 |
| 副本都在，但助记词 / 备份口令丢了 | ❌ | 端到端加密的另一面：没有后门，谁也代不了解密 |

两个物理限制必须讲清楚：

- **离线瞬间不可能有多个物理副本**。断网时只有一台设备，任何「自动保存」都写在同一块磁盘上；清浏览器数据或磁盘损坏会一起带走。要「落笔即冗余」，记账当时就必须有第二个在线副本（另一台常在线设备或可达的服务端）——这是网络条件问题，软件绕不过去。
- **「永远」依赖人和组织**：介质寿命、密钥保管、格式向后兼容、备份是否真的执行并演练过。哈希链只能证明「这段历史没被改过」，不能证明业务真实发生，也不能让消失的介质复原。

已验证的灾难恢复路径（`npm run drill:restore` 自动化演练）：起临时服务写 3 笔 → 生成加密备份 → **关闭服务并删除整个数据目录** → 从备份还原并重启 → 记录数、链头、锚链头、Merkle 根与灾前完全一致，`/api/lookup` 仍能取回加密私钥包与账本目录。结论：**服务器关闭且原盘全丢时，凭「加密备份 + 备份口令 + 用户助记词」可完整找回账本；明文始终需要用户自己的助记词在浏览器里解开。**

### 想更接近「永不丢失」，还差什么

1. **把备份变成自动且多目的地**：现在只是脚本，要自己配 cron / launchd；应改成服务内定时 + 至少两个异地目标（本地盘 + 对象存储），每月自动跑恢复演练。
2. **缩短「只有一份」的窗口**：让第二台常在线设备（家里 NAS / 备用机）持有全量加密副本；离线记账的窗口无法消除，但应在界面明确提示「此笔尚未有第二副本」。
3. **把恢复材料做成自包含的离线包**：助记词 + 备份口令 + 一份加密备份分开保管。归档密钥参数现已随每条归档行导出（`导出加密归档`），单凭助记词 + 归档文件即可在新设备解开，`导入加密归档` 会逐条验签后才写入。
4. 更远的方向：多服务端互备 / 去中心化 relay（Evolu、Anytype any-sync 的做法）、公开时间戳交叉锚定。属于架构级改造，不是补丁。

## 更快的解锁与去中心化可行性

### 已经做的：把「打开到记下」压到最短

| 改动 | 效果 |
|---|---|
| 首页「随手记」 | 金额 + 收支方向 + 可选摘要，一步提交；默认今天与当前账本，连续记账不打断 |
| 本机 PIN 快捷解锁 | 在这台设备设 6 位以上 PIN，之后打开只输 PIN，不必每次抄 16 个助记词 |
| 身份凭据文件 | 导出含助记词 + 私钥的凭据文件；恢复时选「导入身份凭据文件」即可，不依赖服务端，可完全替代手抄的词 |

快捷解锁用**信封加密**：PIN → PBKDF2-SHA256 **60 万次** + 随机 salt → KEK → AES-256-GCM 包住「助记词 + 私钥」，只存本机 localStorage、从不上传；连续 5 次错误自动清除，可随时关闭。`tests/unlock-core.test.mjs` 覆盖降级、错误 PIN、salt 随机性与明文不落盘。

**安全边界（必须说清）**：浏览器 localStorage 没有 Secure Enclave，能接触本机存储的人可以离线尝试 PIN。所以 PIN 是「本机便利」，不是新的身份因子；**助记词仍是唯一跨设备恢复凭据**。业界更优解是 **WebAuthn PRF**——认证器在 Face ID / Touch ID 通过后给出 32 字节确定性输出，不经服务端也不落本地，Bitwarden、1Password 已采用；`pack.method` 已预留 `'prf'`。但 PRF 在浏览器与认证器之间支持仍碎片化（Chromium 系、Safari 18+），所以先落地可测可用的 PIN，保留升级路径。

### 调研结论：去中心化 / 零网是否可行

调研了 Evolu、Anytype any-sync、Automerge Repo、Yjs / Loro、Syncthing Untrusted 模式、libp2p / OrbitDB、Ink & Switch Keyhive，以及 WebAuthn PRF、KeePassXC 2.8 与 PearPass 的快捷解锁实践。结论分层：

| 目标 | 可行性 | 判断 |
|---|---|---|
| 本机快捷解锁 + 一步记账 | ✅ 已实现 | 信封加密成熟，生物识别为升级路径 |
| 无专有云的多设备冗余（托管方看不到明文） | ✅ 可行且零新代码起步 | **Syncthing Untrusted（Receive Encrypted）模式**：可信设备互相同步，另设一个只读密文节点做异地副本。本项目 `events.jsonl` 本就是 append-only 哈希链，天然适合文件级复制 |
| 完全零网（无任何传输通道）自动产生第二副本 | ❌ 物理上不可能 | 没有通道就没有副本。可行的是**延迟同步**：导出加密增量包、AirDrop、局域网碰面时交换。项目已有的「导出 / 导入加密账本」就是 sneakernet 雏形 |
| 局域网自动 P2P（mDNS + WebRTC） | ⚠️ 可做但需常在线节点 | NAT 穿透要 STUN、对称 NAT 要 TURN 中继，且两台设备要同时在场；Syncthing 的实践结论是仍需要常在线 hub |
| 公网纯 P2P + CRDT 自动合并 | ❌ 不适合本项目 | CRDT 的自动合并会破坏「记下就改不了、分叉不合并」的账本语义；Keyhive 类去中心化访问控制仍是预 alpha |

**两个关键判断**：

1. **不要上 CRDT**。本项目是不可变事件日志 + 哈希链，正确的去中心化形态是「多副本 + gossip + 分叉显式保留」，而不是 Automerge / Yjs 的自动合并——对账本来说，合并即篡改。
2. **「无服务器」要重新定义为「无专有云、可自托管、托管方看不到明文」**。业界对纯 P2P 的坦率结论是：仍需要薄中继做身份、缓冲与派发；宣传成「完全没有服务器」是失真的。

### 建议路径

1. ✅ 快捷解锁 + 一步记账（本轮完成）。
2. **加密文件级冗余**：用 Syncthing untrusted 节点同步 `LEDGER_DATA_DIR`，或把 `npm run backup` 的加密产物推到第二个异地目标并自动演练。这一步能真正缩短「只有一份」的窗口，且不改应用代码。
3. **界面显示副本状态**：让用户看到「此笔尚无第二副本 / 已同步到 N 处」，避免误以为记下就永存。
4. 远期才考虑局域网设备直连；多人协作与可撤销权限不要押注 Keyhive 系。
